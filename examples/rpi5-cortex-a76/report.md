## What this means

YES -- your decode is memory-bandwidth-bound.

Token generation is running at 77% of the memory bandwidth this machine can actually sustain. The CPU spends most of each token waiting for weights to arrive from RAM, not computing.

- Model size is your throughput dial. Halving the bytes you load roughly doubles tok/s: a smaller model or a lower quant buys speed almost exactly in proportion to the bytes it removes.
- Measured on your models: Qwen2.5-0.5B Q2_K is 2.91x smaller than Qwen2.5-1.5B Q4_K_M and decodes 2.55x faster. Bytes in, tokens out.
- Best decode thread count: 2. Past that, extra threads add contention, not throughput: decode is waiting on memory, and more waiters do not make the memory faster.
- Using every thread cost up to 21% of decode throughput versus the best setting. Set -t explicitly; do not let it default.
- Prefill is different: it scaled 3.3x with threads (median across your models). Prompt processing is compute-bound, so long-prompt workloads DO want all your cores even though generation does not.

## Caveats

- converted data: measurements come from the published Raspberry Pi 5 study, not from a native llama-roofline run. Bytes-per-token uses the GGUF file size rather than llama-bench's model_size, so utilisation reads ~1-2% high. See convert_paper_data.py for the full provenance note.
- bytes-per-token is taken as the model's resident size. That is exact for a dense transformer at short context and an overestimate once the KV cache grows large, or for MoE models.
- The ceiling was supplied rather than measured by this tool, so every percentage here is only as good as that number.
- Numbers are throughput only. Nothing here measures output quality.
